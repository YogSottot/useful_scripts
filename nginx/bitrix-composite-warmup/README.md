# Bitrix Composite Cache Warmup

`bitrix-composite-warmup.py` — последовательный прогрев композитного HTML-кеша 1С-Битрикс по URL из XML sitemap. Скрипт контролирует системную нагрузку и доступную память, учитывает популярность страниц по nginx `access.log`, сохраняет прогресс в SQLite и поддерживает повторные инкрементальные запуски.

> **Важно:** HTTP 200 не гарантирует, что Битрикс сформировал композитный кеш. Скрипт выполняет HTTP-запросы, а не управляет внутренними механизмами Битрикс. Если кеш уже существует, запрос может получить готовую страницу. Для полной перегенерации предварительно очистите композитный кеш штатными средствами Битрикс. Не удаляйте его вручную без понимания конфигурации.

## Требования

- Linux, Python **3.9+** (используется `Path.is_relative_to`).
- Только стандартная библиотека Python; `pip install` не требуется.
- HTTP(S)-доступ к sitemap и страницам сайта.
- Для приоритизации по nginx — право читать access-логи.
- Для проверки файлового кеша — право читать каталог `bitrix/html_pages`.
- Права на запись в каталог базы SQLite и файлов результатов.

Выполняется **один HTTP-запрос к странице за раз** (без многопоточности). `--max-load` ограничивает **LA за 1 минуту**; это не процент загрузки CPU. Проверка памяти использует Linux `/proc/meminfo` (`MemAvailable`).

## Быстрый старт

```bash
chmod +x bitrix-composite-warmup.py

./bitrix-composite-warmup.py \
  https://example.ru/sitemap.xml \
  --max-load 8 \
  --delay 5 \
  --load-wait 30 \
  --timeout 30 \
  --retries 2 \
  --state /var/tmp/example-warmup.done \
  --failed /var/tmp/example-warmup.failed
```

Этот вариант **совместим с прежним запуском**. При отсутствии `--db` SQLite создаётся в текущем рабочем каталоге под именем `bitrix-warmup.sqlite3`. Для нескольких сайтов задавайте **разные файлы базы**.

### Рекомендуемый запуск

```bash
./bitrix-composite-warmup.py \
  https://example.ru/sitemap.xml \
  --max-load 8 \
  --delay 5 \
  --adaptive-delay \
  --load-wait 30 \
  --min-mem-mb 1024 \
  --timeout 30 \
  --retries 2 \
  --backoff-max 300 \
  --access-log '/var/log/nginx/example.ru.access.log*' \
  --db /var/tmp/example-warmup.sqlite3 \
  --state /var/tmp/example-warmup.done \
  --failed /var/tmp/example-warmup.failed
```

Путь к логам зависит от конфигурации nginx. Если используете проверку файлового кеша, добавьте, **только после проверки расположения файлов**:

```bash
  --cache-dir /var/www/bitrix/example.ru/bitrix/html_pages \
  --cache-max-age-days 7
```

`--cache-dir` необязателен и по умолчанию **выключен**.

## Параметры командной строки

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `sitemap` | обязателен | URL `sitemap.xml` или sitemap index (HTTP/HTTPS) |
| `--max-load` | `8.0` | Максимальный LA за 1 минуту; выше порога запросы не выполняются |
| `--delay` | `5.0` | Базовый интервал между началами HTTP-запросов к страницам, в секундах |
| `--adaptive-delay` | выключен | Меняет интервал в зависимости от LA |
| `--load-wait` | `30.0` | Интервал повторной проверки LA/RAM при превышении порогов, секунды |
| `--min-mem-mb` | `1024` | Минимальный `MemAvailable`, МиБ; `0` отключает контроль RAM |
| `--timeout` | `30.0` | Таймаут HTTP-запроса, секунды |
| `--retries` | `2` | Число **дополнительных** попыток, всего до 3 |
| `--backoff-max` | `300` | Верхний предел задержки при повторах, секунды |
| `--db` | `bitrix-warmup.sqlite3` | База SQLite с состоянием страниц |
| `--state` | `bitrix-warmup.done` | Старый текстовый список успешных URL: импортируется однократно и пополняется |
| `--failed` | `bitrix-warmup.failed` | Дополняемый журнал неудач и 404 |
| `--access-log` | нет | Один или несколько nginx combined log; поддерживаются glob и `.gz`, можно повторять аргумент |
| `--include-bots` | выключен | Включить обращения ботов в расчёт популярности |
| `--cache-dir` | нет | Корень файлового кеша `bitrix/html_pages` для проверки наличия файла |
| `--cache-max-age-days` | `0` | Максимальный возраст файла кеша в днях; `0` — возраст не проверять |
| `--refresh-days` | `0` | Повторно обрабатывать успешные URL старше N суток; `0` отключает |
| `--full` | выключен | Сбросить статусы страниц из текущего sitemap в `pending` для полного повторного обхода |
| `--limit` | `0` | Максимум выбранных URL за запуск; `0` — без лимита |
| `--help` | — | Полная справка |

### Адаптивная пауза

При `--adaptive-delay` выбирается задержка по отношению `LA / --max-load`:

| Уровень LA относительно лимита | Интервал при `--delay 5` |
|---|---:|
| ≤ 25% | 0,5 с |
| ≤ 50% | 1 с |
| ≤ 75% | 2 с |
| ≤ 87,5% | 5 с |
| ≤ 100% | 10 с |
| > 100% | ожидание `--load-wait`, запрос не начинается |

Пауза считается **между моментами начала HTTP-запросов**, а не как обязательный сон после завершения каждого ответа. При включённом адаптивном режиме пауза может быть **меньше 5 секунд**; если необходим строгий интервал не менее 5 секунд, **не используйте** `--adaptive-delay` (и помните, что интервалы при повторных попытках управляются отдельно).

Порог LA — абсолютный, без нормализации по числу CPU. При недоступном `MemAvailable` скрипт не блокирует запросы из-за RAM; на Linux рекомендуется проверять, что `/proc/meminfo` доступен.

## Sitemap и порядок обхода

Поддерживаются XML `urlset`, `sitemapindex`, вложенные sitemap, gzip-сжатые карты (`.xml.gz` либо gzip по сигнатуре). URL дублируются в SQLite только один раз. Принимаются только HTTP(S)-адреса **того же hostname**, что и исходный sitemap. URL с query string или fragment не добавляются в очередь. Редиректы на другой hostname запрещены.

Ограничения чтения одной карты: **50 МиБ** на полученное тело и **100 МБ** после распаковки gzip. XML отдельной карты разбирается в памяти (не streaming parser).

Очередь сортируется по:

1. Числу принятых обращений (`hits`) из access.log — по убыванию.
2. `lastmod` из sitemap — сначала более новые.
3. URL — лексикографически.

Если `--access-log` не указан, все URL имеют приоритет `hits=0`.

## Приоритизация по nginx access.log

Нужен формат nginx **combined**, например:

```text
68.220.62.154 - - [02/Nov/2026:03:13:16 +0300] "GET /catalog/item/ HTTP/2.0" 200 236007 "-" "Mozilla/5.0 ... Chrome/152.0.0.0 Safari/537.36"
```

Принимаются только запросы `GET` с кодом **200**, без query-параметров, по путям, совпадающим с URL текущего sitemap. Запросы ботов/мониторинга по User-Agent отбрасываются эвристически (в том числе `Reflectionbot`, `BitrixCloud Monitoring`, `curl`, `wget`, типичные `bot`, `crawl`, `spider`). `--include-bots` отключает эту фильтрацию. Подделанный браузерный User-Agent фильтр может не распознать.

Несколько логов и gzip-архивы:

```bash
--access-log '/var/log/nginx/example.ru.access.log*'
```

Или явно (в том числе повторяя параметр):

```bash
--access-log /var/log/nginx/example.ru.access.log /var/log/nginx/example.ru.access.log.1 \
--access-log /var/log/nginx/example.ru.access.log.2.gz
```

Маску рекомендуется **заключать в кавычки**, чтобы её обрабатывал сам скрипт. Совпавший в нескольких масках один и тот же файл учитывается один раз по разрешённому пути. Данные популярности **обнуляются и пересчитываются по переданным логам при каждом запуске**; история популярности в SQLite не накапливается. Ротация/сжатие логов не выполняются скриптом.

Примечание: если в логах нескольких виртуальных хостов одинаковые URL-пути, но нет поля `$host`, записи невозможно однозначно разделить по сайту. Передавайте **логи только нужного виртуального хоста**. Лог-форматы, отличные от стандартного combined, могут не распознаваться.

## SQLite и инкрементальный режим

Инкрементальный режим **включён по умолчанию**; опции `--incremental` нет.

| Текущее состояние URL | Следующий обычный запуск |
|---|---|
| Не встречался ранее | Выполнить запрос |
| `pending` (не обработан) | Выполнить запрос |
| `done` (HTTP 200 ранее) | Пропустить, пока `lastmod` не изменится |
| `not_found` (HTTP 404) | Пропустить, пока `lastmod` не изменится |
| `failed` (иная ошибка) | Попробовать снова |
| `cached` (пропущен по наличию файла) | Перепроверить файл; если он исчез/устарел — запросить URL |

При изменении **существующего непустого** `lastmod` на другое непустое значение статус меняется на `pending`. Если `lastmod` отсутствует, изменённую страницу скрипт автоматически не обнаружит. Данные `lastmod` должны корректно обновляться самим сайтом.

Принудительный обход всех URL:

```bash
./bitrix-composite-warmup.py https://example.ru/sitemap.xml \
  --db /var/tmp/example-warmup.sqlite3 --full
```

> При `--full` и одновременно заданном `--cache-dir` страницы с обнаруженным свежим файлом **всё равно пропускаются**. Для безусловных HTTP-запросов по всем URL не указывайте `--cache-dir`.

Перепроверять успешные URL, обработанные более 7 суток назад:

```bash
./bitrix-composite-warmup.py https://example.ru/sitemap.xml \
  --db /var/tmp/example-warmup.sqlite3 --refresh-days 7
```

`--refresh-days` действует на статус `done`, а не на `not_found`. В текущей реализации импортированные из `.done` записи имеют пустое `last_success`, поэтому сами по себе не попадают под обновление по `--refresh-days`, пока не будут реально обработаны.

Для ограниченного прогона (например, первые 1000 приоритетных URL):

```bash
./bitrix-composite-warmup.py https://example.ru/sitemap.xml \
  --db /var/tmp/example-warmup.sqlite3 \
  --access-log '/var/log/nginx/example.ru.access.log*' \
  --limit 1000
```

URL, отсутствующие в текущем sitemap, остаются в SQLite, но не входят в текущую очередь.

### Файлы состояния

- `bitrix-warmup.sqlite3` — основное состояние страниц и результаты запросов. SQLite использует WAL; во время работы могут существовать сопутствующие файлы `-wal` и `-shm`.
- `bitrix-warmup.done` — дополняемый список URL с успешным HTTP 200. При **первом** запуске с данной БД существующий `.done` однократно импортируется. Позднейшее редактирование `.done` не синхронизируется обратно с SQLite.
- `bitrix-warmup.failed` — дополняемый журнал ошибок (`404 URL`, `503 URL`, `ERROR URL` и т. д.). Это **история событий**, а не актуальный список неуспешных страниц; повторы и старые ошибки остаются в файле.

Для инспекции базы:

```bash
sqlite3 /var/tmp/example-warmup.sqlite3 \
  'SELECT status, COUNT(*) FROM pages GROUP BY status ORDER BY status;'

sqlite3 /var/tmp/example-warmup.sqlite3 \
  "SELECT hits, url FROM pages ORDER BY hits DESC LIMIT 20;"
```

Не запускайте одновременно несколько копий скрипта с **одной** SQLite-базой: механизм межпроцессной координации прогрева не реализован.

## Проверка файлового композитного кеша

Включается только через `--cache-dir`. Скрипт **не удаляет и не изменяет** файлы кеша. Для типовой структуры предполагается:

```text
<cache-dir>/<hostname>/<uri>/index@.html   # URI оканчивается /
<cache-dir>/<hostname>/<uri>@.html         # URI без завершающего /
```

Например, для `https://example.ru/catalog/` проверяется:

```text
/var/www/bitrix/example.ru/bitrix/html_pages/example.ru/catalog/index@.html
```

Существующий непустой файл считается пригодным, если:

- его `mtime` не старше указанного `lastmod` (когда он есть);
- его возраст не превышает `--cache-max-age-days` (если задано значение > 0).

**Ограничения:** это эвристика для типовой файловой схемы. Реальные пути и ключи кеша зависят от конфигурации nginx/Битрикс, протокола, домена, дополнительных факторов и правил URL. Наличие файла не доказывает, что кеш корректный и отдаётся посетителям. Для нестандартной конфигурации лучше **не использовать `--cache-dir`**, чем пропустить нужные запросы.

## Ошибки, повторы и нагрузка

- **200:** успех (`done`); сохраняются время, длительность и значение заголовка `X-Bitrix-Composite` (если есть).
- **404:** без повторных попыток (`not_found`); запись в `.failed`.
- **429 / 503:** дополнительные попытки с экспоненциальной задержкой, учитывается `Retry-After` в пределах `--backoff-max`.
- **Прочие HTTP-ошибки и сетевые сбои:** дополнительные попытки с задержкой; после исчерпания попыток — `failed`.
- **Редиректы:** допускаются внутри того же hostname; конечный HTTP 200 будет принят.
- **LA выше лимита или недостаточно RAM:** перед запросом ожидание `--load-wait` и повторная проверка. Контроль также проводится перед повторными попытками.

Для планового фонового режима рекомендуется запускать скрипт с отдельной базой для каждого сайта и использовать `flock` от параллельного запуска:

```bash
flock -n /var/lock/example-bitrix-warmup.lock \
  /usr/bin/python3 /opt/scripts/bitrix-composite-warmup.py \
  https://example.ru/sitemap.xml \
  --db /var/tmp/example-warmup.sqlite3 \
  --access-log '/var/log/nginx/example.ru.access.log*' \
  --adaptive-delay --max-load 8 --delay 5
```

Если конфигурация использует nginx на одном сервере и PHP/MySQL на другом, локальный LA и `MemAvailable` отражают **только машину, где запущен скрипт**, а не нагрузку удалённой БД/PHP.

## Коды завершения

| Код | Значение |
|---|---|
| `0` | Обход завершён без не-404 ошибок, исчерпавших попытки; наличие 404 допустимо |
| `1` | Есть URL, для которых исчерпаны попытки, либо необработанное исключение Python |
| `130` | Остановка по `Ctrl+C` (`KeyboardInterrupt`); прогресс в SQLite сохранён |

## Диагностика

```bash
python3 bitrix-composite-warmup.py --help
python3 -m py_compile bitrix-composite-warmup.py
```

Проверьте, что sitemap содержит правильные URL, `access.log` относится к нужному vhost, у процесса есть доступ к SQLite/логам/кешу и что запросы действительно формируют композитную HTML-страницу. Для проверки результата используйте заголовки ответа и настройку композитного кеша в Битрикс; один лишь код HTTP 200 недостаточен.
